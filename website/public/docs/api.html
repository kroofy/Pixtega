API reference

The entire API is one endpoint, answering GET and HEAD. Everything else — method, path shape, transform, query string — is strictly validated, and every derived image has exactly one URL.

URL grammar#

GET /images/{mount}/{source-path}/{transform}

Example:

GET /images/public/photos/example.6acca6c1.jpg/w1280.webp
  • {mount} selects a configured source. Callers can never supply a hostname, bucket, directory, or transport.
  • {source-path} is everything between the mount and the final segment. It is opaque, decoded exactly once, and strictly validated: no traversal, no encoded delimiters, canonical percent-encoding only.
  • {transform} is the final segment: w{width}[,q{quality}].{format} with format one of webp, avif, jpeg (no aliases). Width must be in the configured allowlist; quality must be in the selected format's allowlist. Omitting q uses the format's default; spelling out the default is rejected, so each derived image has exactly one URL.
  • No query parameters are defined: any non-empty query string is a 400, so each derived image has exactly one URL.
  • GET and HEAD are supported; HEAD returns exactly the GET response — same status and headers, including Content-Length — with the body dropped. Anything else is 405, with an Allow: GET, HEAD header. Request targets over 8192 bytes are rejected.

The service never upscales: a source narrower than the requested width keeps its original dimensions.

Caching#

ResponseCache-Control
200public, max-age={success_ttl_seconds}, plus , immutable when success_immutable = true
304same policy the matching 200 would have used
404public, max-age={not_found_ttl_seconds}
every other errorno-store
Recommended: content-hashed source names, cached for one year. Give every source image a strongly identifying name — a content hash such as photos/example.6acca6c1.jpg — and never overwrite it. A path then always means the same bytes, so there is no reason to cache it for less than a year. 
success_ttl_seconds = 31536000
success_immutable = true

Every 200 (and 304) is then served with public, max-age=31536000, immutable, and changing an image means publishing it under a new name.

If your source paths can be overwritten, the lifetime is at your discretion: leave success_immutable off and pick a success_ttl_seconds you can live with. The service has no cache-busting parameter, so a changed image at the same path is only picked up once that lifetime runs out. Never set success_immutable = true for paths that can change.

Errors#

Errors are JSON: { "error": "message" }.

StatusMeaning
400invalid path, mount, query, transform, width, format, or quality
404the source answered authoritatively that the object is absent
405method other than GET or HEAD
500flatten/encode failed after a valid source was accepted
502source answered without a usable object: permission denied, unexpected upstream status, oversized content, undecodable or unsupported image bytes
504fetching the source timed out, or the whole request exceeded request_timeout_ms

Permission denial is always 502, never 404, so a misconfigured bucket cannot be cached as "missing".

Response headers#

Successful 200 responses carry the derived image's Content-Type, the Cache-Control policy above, and an ETag when the source exposed an object identity (S3 ETag/VersionId, HTTP ETag, or filesystem mtime+size+key). The tag combines that identity with the resolved transform. Weak upstream tags stay weak; filesystem identity is always weak. If-None-Match matching that tag is 304 Not Modified with the same cache policy, no body, and no source-body fetch or encode. A HEAD the origin refuses (other than timeout) is ignored and the service fetches instead. There is no Last-Modified. Every response — success or error — also carries X-Content-Type-Options: nosniff, Content-Security-Policy: default-src 'none', and X-Frame-Options: DENY.

Observability#

The service emits one structured JSON completion event per request on stdout, with status, a stable outcome from a closed set (success, rejected_request, not_found, timeout, source_too_large, source_unavailable, undecodable_source, flatten_failed, encode_failed), mount, output width/format, upstream status, byte counts, and elapsed milliseconds. A source failure with an internal detail (S3 dispatch vs service error, HTTP connect vs unexpected status) also emits a separate {"event":"source_error","level":"warn","detail":"..."} line immediately before request_completed. detail never appears in the client JSON body. Response bodies, credentials, and query strings are never logged.

Path validation and adapter behavior are covered further in the README and pinned down by the project's test suite.
